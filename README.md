# hivemind-ma-player

Music Assistant PlayerProvider that drives a **remote** OpenVoiceOS (OVOS) instance through a
[HiveMind](https://github.com/JarbasHiveMind/HiveMind-core) encrypted websocket connection.

HiveMind is a secure overlay on top of the OVOS messagebus. It wraps each OVOS/Mycroft message
in an authenticated envelope and transports it over a `wss://` connection. This plugin uses
exactly the same OCP bus messages as
[ovos-ma-player](https://github.com/TigreGotico/ovos-ma-player) — the only difference is the
transport layer. Because HiveMind is multi-client, one Music Assistant server can control
multiple remote OVOS devices simultaneously, each as its own provider instance.

**Typical use case:** Music Assistant running on a home server; OVOS devices scattered around the
house (Raspberry Pis, desktops, etc.), each running HiveMind. Add one `hivemind-ma-player`
instance per device in the MA UI.

## Prerequisites

| Requirement | Notes |
|---|---|
| Python 3.11+ | Required by both MA and this plugin |
| Music Assistant | The server that this plugin extends |
| OVOS with OCP | Must be running on each remote device |
| HiveMind | Must be installed and running on each remote OVOS device. See [HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core). |
| Access key | Generated on the remote device with `hivemind-core add-client` |

---

## Install

```bash
pip install hivemind-ma-player
```

Music Assistant discovers the plugin automatically via the `music_assistant.provider` entry-point
group (key `hivemind_player`, declared in `pyproject.toml`). After installation, restart MA.
The provider appears in the UI under **Players > Add Provider**. Because `multi_instance: true`
is set in the manifest, you can add one instance per remote OVOS device.

---

## Getting an access key

On the machine running HiveMind (the remote OVOS device):

```bash
pip install hivemind-core
hivemind-core add-client --name "music-assistant"
```

This prints an access key (and optionally a password). Copy those values into the MA
configuration form. The key is stored in HiveMind's database and validated on every connection
attempt.

To list existing clients:

```bash
hivemind-core list-clients
```

To revoke access:

```bash
hivemind-core delete-client --name "music-assistant"
```

## Configuration

| Key | Type | Default | Required | Description |
|---|---|---|---|---|
| `host` | string | — | **yes** | Hostname or IP of the HiveMind node (e.g. `myrpi.local`, `192.168.1.42`). |
| `port` | integer | `5678` | no | HiveMind WebSocket port. Change only if HiveMind was started with a non-default port. |
| `access_key` | secure string | — | **yes** | The key generated by `hivemind-core add-client`. Stored encrypted by MA. |
| `password` | secure string | — | no | Optional password, only if you passed `--password` during `add-client`. |
| `ssl` | boolean | `true` | no | Whether to use `wss://` (encrypted). Disable only on trusted local networks for debugging. |
| `player_name` | string | `MA HiveMind Player` | no | Display name shown in the MA UI for this player. Useful when you have multiple HiveMind instances. |

**Recommendation:** always leave `ssl: true`. HiveMind encrypts the payload regardless, but TLS
also authenticates the server certificate.

## How it works

### Connection

On provider init, `HiveMindPlayerProvider.handle_async_init` creates a
`HiveMessageBusClient(key, host=host, port=port, password=password, ssl=ssl)` and calls
`bus.connect(FakeBus())` in a daemon thread. `FakeBus` is the local side of the HiveMind
tunnel — HiveMind uses it internally to route messages between the remote OVOS bus and the
local client. MA waits up to 15 seconds for the connection to complete; if it fails or times out,
`ProviderUnavailableError` is raised.

### Player registration

`discover_players` registers a single `HiveMindPlayer` with player ID `<instance_id>:hivemind`.
The player name is taken from the `player_name` config entry (defaults to
`"MA HiveMind Player"`).

### Command flow (MA → remote OVOS)

Playback commands call `HiveMindPlayer._emit(msg_type, data)`, which wraps the message in a
`HiveMessage` envelope and calls `bus.emit_mycroft(msg)`. HiveMind encrypts and transmits the
envelope to the remote node, which unwraps it and emits the inner OVOS `Message` on the local
bus of the remote OVOS instance.

| MA action | OCP message emitted | Payload |
|---|---|---|
| Play (resume) | `ovos.common_play.resume` | — |
| Pause | `ovos.common_play.pause` | — |
| Stop | `ovos.common_play.stop` | — |
| Seek | `ovos.common_play.set_track_position` | `{"position": <float seconds>}` |
| Volume | `mycroft.volume.set` | `{"percent": <0.0–1.0>}` |
| Mute | `mycroft.volume.mute` | — |
| Unmute | `mycroft.volume.unmute` | — |
| Play media | `ovos.common_play.play` | `{"media": <MediaEntry dict>}` |
| Announcement | `ovos.common_play.play` | `{"media": <MediaEntry dict>}` |

For `play_media` and `play_announcement`, MA resolves the stream URL via
`mass.streams.resolve_stream_url`, builds an OCP `MediaEntry`, and emits
`ovos.common_play.play`.

**Important:** the stream URL must be reachable from the remote OVOS device, not just from the
MA server. If OVOS is on a different subnet, use MA's external/public URL in the stream
settings.

### State sync (remote OVOS → MA)

State is kept in sync by the same two mechanisms as the local provider:

**Push (event-driven):** The provider subscribes to `ovos.common_play.player.state` and
`ovos.common_play.media.state` on the HiveMind bus. HiveMind tunnels these events from the
remote OVOS bus back to MA automatically.

**Pull (polling fallback):** `poll()` sends `ovos.common_play.status` and calls
`bus.wait_for_response(..., reply_type="ovos.common_play.status.response", timeout=3.0)`.
`wait_for_response` registers the reply listener atomically before sending, avoiding the race
condition where the response arrives before the listener is registered. The response is a
`HiveMessage`; the inner OVOS `Message` is accessed via `resp.payload`. Poll runs every 5 s
while playing, every 30 s otherwise.

## Troubleshooting

**Provider stays "unavailable" after saving config**
- Verify HiveMind is running on the remote device: `systemctl status hivemind` or equivalent.
- Test connectivity: `curl -v wss://<host>:<port>` (expect a 101 upgrade or a 401, not a
  connection refused).
- Confirm the access key is correct by running `hivemind-core list-clients` on the remote.
- If you generated the key with `--password`, ensure you also entered it in MA.

**"HiveMind connection failed: authentication error"**
- The access key was rejected. Re-run `hivemind-core add-client --name "music-assistant"` and
  update the MA config with the new key.

**Playback starts on MA but no audio on the remote device**
- Confirm OCP is installed on the remote OVOS: `pip show ovos-skill-ocp` (on the remote).
- Check OVOS logs on the remote device.
- Verify the stream URL is reachable from the remote device:
  `curl -I <stream-url>` (on the remote).

**State in MA is always IDLE**
- HiveMind must be configured to tunnel `ovos.common_play.*` events back to clients. Check
  HiveMind's `allowed_messages` config on the remote.
- Run `hivemind-client terminal` to observe bus traffic through the tunnel.

**Multiple devices: players have the same name**
- Set a unique `player_name` for each provider instance in the MA UI.

## Developer notes

- `HiveMindPlayerProvider` and `HiveMindPlayer` mirror `OVOSPlayerProvider`/`OVOSPlayer` from
  `ovos-ma-player`. The only structural difference is the bus type (`HiveMessageBusClient` vs
  `MessageBusClient`) and the `_emit` helper on `HiveMindPlayer` which calls
  `bus.emit_mycroft()` instead of `bus.emit()`.
- All `ovos_bus_client`, `hivemind_bus_client`, and `ovos_utils` imports are deferred to
  `handle_async_init` or method bodies to avoid hard failures when the packages are absent.
- The `multi_instance: true` manifest flag is what allows multiple instances in MA.

See [`docs/architecture.md`](docs/architecture.md) for the full class diagram, OCP/HiveMind
message reference, and threading model, and [`docs/plugin-authors.md`](docs/plugin-authors.md)
for guidance on forking and extending the plugin.
